# Yonaris Site 09 全站高保真交互原型设计规范

## 状态与适用范围

- 状态：设计方向与本书面规范均已由用户确认，可进入原型实施计划。
- 本文件取代 `2026-08-28-site-09-product-truth-redesign.md` 作为 Site 09 的唯一设计依据。
- 当前阶段只制作独立本地原型，不修改、不发布 `yonaris-site` 生产页面。
- 首轮范围为英文站六个完整页面：Home、Product、Approach、Human / Agent、Casework、Contact。
- 中文站在英文体验系统成立后单独设计。它沿用同一视觉与交互质量，不翻译英文信息架构。

## 1. 已确认的核心判断

Site 08 不是需要继续精修的页面模板，而是视觉气质基线。

允许从 Site 08 页面设计语言中继承的资产只有（不影响 Yonaris Logo、wordmark 等正式品牌标识继续使用）：

1. 深蓝、暖米白与橙色信号色构成的企业级气质；
2. 全幅影像、留白与强排版带来的空间张力；
3. Human / Evidence / Agent 三层证据透镜的交互思想；
4. 英文站面向海外用户独立组织叙事的原则。

不得继承的资产包括：

- Site 08 六页重复的 Hero、四栏信息与尾部 CTA 骨架；
- 巨大断行标题、全大写橙色眉题、微型等宽字、编号、细线和状态标签组成的默认“AI 网站语法”；
- 仿后台的硬编码产品界面；
- 为制造真实感而堆砌的数量、哈希、URL、时间、排名或效果指标；允许使用由单一记录模型驱动、内部一致且不冒充客户或生产数据的确定性演示 fixture；
- `Vendor A`、`Illustrative pattern` 等伪精确案例；
- 黑暗会议室、玻璃办公楼和摆拍商务人物组成的通用 AI 企业摄影；
- 把桌面模块纵向堆叠成移动页面的适配方式；
- 已被否决的 Site 09 静态原型及其页面结构。

## 2. 品类与产品表达

Canonical category：

> AI-Native MarTech Infrastructure

GEO 是第一个可观察入口，不是 Yonaris 的品类终局。网站必须表达 Yonaris 是贯穿以下系统的 MarTech Control Point：

> Observe → Interpret → Execute → Outcome → Learn

产品表达可以使用 BP 中的 Product Truth、Market Intent、Model / Agent Behavior、Commercial Response、Decision Event、Evidence Grade、Outcome Spec、Outcome Proof 和 Decision Signals，但这些词不能在面向客户的正文中堆叠。公开文案先讲客户问题、系统动作和商业意义，再在需要时给出准确术语。

全球能力不建立独立的 `Global Markets` 叙事。市场、语言、来源和适用边界自然存在于每一次观察、案例和证据记录中。不得把全球服务简化为“中国企业出海”或“国际公司进入中国”。

## 3. 产品展示的真实性边界

官网不是 Portal 操作手册，也不要求忠实复刻 Portal UI。Site 09 使用一个独立的产品演示层（demonstration layer）：

- 能力边界真实：展示的观察、解释、行动、验证与学习必须属于 Yonaris 已有或已明确规划的能力；
- 因果关系真实：输入、信号、证据、人工判断和结果之间必须存在可理解的连续关系；
- 表现可以超越产品：界面可被重组、抽象、放大、压缩时间和电影化编排；
- 不伪造证明：不得制造客户 Logo、客户引语、收入、排名、提升百分比、实时状态或精确客户结果；
- 示例可为代表性演示场景，但不得伪装成真实客户数据或生产记录；
- 原型不接入实时 Portal，也不依赖 LAS。正式实现是否复用产品数据模型在后续实施计划中决定。

核心原则：

> 视觉可以超过后台，能力边界不能超过后台。

## 4. 全站体验架构

六个页面共享品牌气质、动效语法和内容真实性规则，但不共享同一个页面模板。每个页面只有一个主事件。

### 4.1 Home - Market Decision Field

首页不是“左侧品牌文案 + 右侧产品卡片”，而是一整个连续、可操作的市场决策场。

首屏的演示过程：

1. 一个具体商业问题进入场景；
2. AI、搜索、公开内容与比较环境中的市场回应以不同轨迹出现；
3. 大量信息被压缩为少数决定性事实、来源、缺口与边界；
4. Human Review 介入并检查事实、证据、范围和判断；
5. 当证据被补充或边界被澄清，比较依据与选择条件发生可解释的变化；这不是排名或份额提升声明；
6. 一个代表性的 Commercial Response 或 Outcome 信号回到系统，形成最小但完整的学习闭环；
7. 演示自然收束到查看能力、打开案例或提交真实市场问题。

交互规则：

- 进入视口时运行一段短预演，保证第一眼具有生命力；
- 用户点击、拖动、悬停或键盘操作后立即转为手动控制；
- 支持暂停、拖动、重播和 Human / Agent 切换；
- 不显示传统轮播点、步骤卡或孤立进度条；
- 所有状态变化发生在同一视觉场中，不以换标题冒充系统工作；
- 首屏文案必须表达商业问题与品类宽度，不能让公司看起来只是 GEO 工具。

### 4.2 Product - MarTech Control Point

Product 页的主角不是后台界面，而是一个持续变化的“决策对象”。用户通过滚动、拖动和聚焦信号，让同一个对象穿过五种产品状态：

1. **Observe**：同一个市场问题在 AI、搜索、公开内容和比较环境中展开；
2. **Interpret**：回答被解析为决定性事实、来源、缺口、Evidence Grade 和适用边界；
3. **Execute**：证据缺口连接到内容、品牌表达、Demand Gen 与 Commercial Response 等动作；
4. **Outcome**：冻结问题、市场、模型范围和比较条件，对照行动前后的 Decision Event 与 Outcome Proof；
5. **Learn**：商业响应、结果证明与新观察回到系统，形成 Decision Signals 和学习回路。

这五个状态不得呈现为五张卡或常规 Tab。它们共享同一个连续舞台，但每个状态具有不同的空间构图和操作方式：

- Observe 是展开的市场信号场；
- Interpret 收缩为证据关系；
- Execute 变成行动路径和系统重新布线；
- Outcome 形成可比较的冻结截面；
- Learn 重新组成循环网络。

### 4.3 Approach - Outcome Spec in Formation

Approach 页解释怎样与客户一起工作，而不是再展示四步方法卡。

页面围绕一份不断形成的 Outcome Spec 展开：

- 客户的真实问题和判断条件被固定；
- 市场观察进入工作现场；
- 决定性证据与缺口被圈出；
- Human Review 写入适用范围、限制和判断；
- 干预动作被连接到对应证据；
- 同条件重新观察并形成可审查结果。

整个页面应像一个工作现场逐渐完成。它必须让用户理解 Yonaris 如何承担判断责任、如何保留证据，以及哪里仍需要客户或人工决定。

### 4.4 Human / Agent - Two Readings, One Truth

Human / Agent 同时是一项全站阅读模式、一个标志性交互页面，以及正式实现中的机器可读发布层。

#### 局部证据透镜

保留三层圆环，但不再只做遮罩：

- Human 层保留完整表达与业务语境；
- Evidence 层把当前句子解析为 claim、fact、source、scope 和 boundary；
- Agent 层显示结构化记录、稳定 ID 与来源关系。

移动透镜时，被检查的句子与相邻记录真实建立映射和重排。

#### 整页转换

全站顶部始终存在明显的 Human / Agent 控制器。拖动控制器时：

- 影像、装饰和叙事结构逐步退场；
- 标题与段落拆解为事实单元；
- 来源、时间、范围和关系继续附着；
- 页面收束为紧凑的 Agent record。

用户选择的阅读模式在六页本地导航中保持，除非用户主动切换或重置；不得在每次换页后悄悄恢复默认模式。

事实保留数量和内容压缩程度必须由当前演示记录计算，禁止写死 `0 facts lost`。

原型阶段即必须由同一份 canonical demonstration record 生成 Human、Evidence 与 Agent 三态。三态共享稳定 fact/source ID 和来源关系，并提供可直接访问的本地 Agent record；禁止为三种阅读模式分别硬写互不关联的 DOM 或文案。SSR、线上抓取、canonical、sitemap 与部署层语义留到正式实现。

#### 正式实现的语义要求

视觉转换不能被描述成自动提升排名或收录。生产实现需要让视觉演示对应真实的服务端内容、语义化 HTML、结构化数据、稳定事实与来源 ID、可访问的 Agent record、canonical、sitemap 与抓取策略。它提高可提取性和可信度，但不承诺 Google 排名或 AI 引用结果。

### 4.5 Casework - Evidence and Time Section

Casework 使用脱敏结构，不制造客户证明。

用户拖动一个时间或证据截面，在同一个问题下检查：

- 初始回答依赖哪些依据；
- 哪条决定性证据来自第三方；
- 哪个事实此前不可验证；
- Yonaris 采取了什么动作；
- 再次观察后哪些依据改变；
- 哪些事实、限制或结果没有改变。

演示可以高度导演化，但变化必须能追溯到来源和动作。禁止使用突然上涨的百分比代替 Outcome Proof。

### 4.6 Contact - Progressive Human Intake

Contact 从观看体验自然进入行动，不提供虚假的即时审计。

第一阶段只收集：

- 公司或网站；
- 一个真实市场问题。

第二阶段再收集联系人和必要背景。页面必须清楚说明：

- 提交由团队人工评估；
- 不会自动生成假报告；
- 用户会收到适配判断、建议起点和后续沟通方式。

正式原型可以演示成功、错误与保留输入状态，但不触发真实外部邮件或生产 API。

## 5. 视觉系统

### 5.1 保留

- Site 08 的深蓝、暖米白和橙色信号色；
- 成熟、克制、企业级的总体气质；
- 全幅影像、留白和大尺度空间；
- 编辑感与技术感并存；
- 圆环、显影和证据附着作为 Yonaris 视觉母题。

### 5.2 改变

- 无衬线字体承担品牌主张与产品动作；衬线字体只用于观点、证据和案例结论；
- 等宽字体只用于真实数据与机器结构，不作为全站装饰；
- 标题不得依赖五六行强制断行制造气势；
- 页面不得采用统一的 Hero、四栏卡片和尾部 CTA 模板；
- 产品界面、影像和动态必须处于同一个空间，不在背景图上覆盖漂浮 SaaS 卡片；
- 不照搬 Bluefish 的页面几何、文案、影像和标志性构图，也不照搬 Scrunch 的粒子、浏览器框或 Token Reduction 特效。

### 5.3 原创影像方向

首轮影像以三个可验证母题建立统一世界：

- **Refraction / 折射**：同一事实在不同信息环境中如何被看见；
- **Selection / 选择**：注意力、证据与候选如何被聚焦；
- **Boundary / 边界**：事实适用于哪里，又在哪里停止成立。

人物可以出现，但应像真实决策现场的片段，不是企业宣传照。光线、玻璃、纸面、屏幕和人的动作需要形成连续的艺术指导。该方向是原型假设，最终以实际页面是否高级、有辨识度且没有通用 AI 摄影感为判断标准。

### 5.4 动效分工

- 环境动效维持生命力和空间感；
- 操作反馈让用户感到系统受其控制；
- 因果动效解释输入、证据、判断与结果之间的关系；
- 滚动淡入可作为弱层存在，但不能承担主要体验；
- `prefers-reduced-motion` 必须保留完整信息和操作结果。

## 6. 文案与本地化

英文站使用海外 B2B 买家和投资人的认知路径：先说明市场变化、客户风险与商业意义，再解释系统和方法。不得把中文结构翻译成英文，也不得让内部框架词替代客户语言。

中文站不采用另一套低配视觉风格。它将在英文体验系统成立后，围绕国内客户的具体焦虑、先进性判断和采购习惯重新组织内容。两种语言共享品牌视觉、产品能力和事实来源，不共享机械的信息结构。

## 7. 本地原型交付

下一次视觉交付为一个本地可点击地址，而不是 PNG 集合或生产页面。

原型必须包含：

- 英文六页完整导航；
- Home 的连续市场决策场；
- Product 的五态 Control Point；
- Approach 的 Outcome Spec 工作现场；
- 全站 Human / Agent 控制器、局部证据透镜和整页转换；
- 由同一 canonical record 生成的 Human、Evidence、Agent 三态，以及可直接访问的本地 Agent record；
- Casework 的可操作证据 / 时间截面；
- Contact 的渐进式表单演示；
- 为桌面与移动分别编排的布局；
- 键盘可操作、可暂停、可重播和 reduced-motion 行为；
- 一个清楚但不冒充客户数据的演示场景声明。

原型不包含：

- 生产 API、邮件投递或 LAS 依赖；
- Vercel 发布与域名切换；
- 中文站页面实现；
- 客户 Logo、引语或未经提供的真实材料；
- 实时抓取、即时审计或模型调用；
- Portal UI 的逐像素复制。

## 8. 原型验收标准

在提交给用户前必须满足：

1. 五秒内能够理解 Yonaris 是 AI-Native MarTech Infrastructure，而不只是 GEO；
2. 首页本身是一项可操作的产品体验，而非静态 Hero；
3. Product 清楚表达 Observe、Interpret、Execute、Outcome 与 Learn 的 Control Point；
4. Human / Agent 在全站显著，并把相同事实从表达连续转换为证据与结构；
5. 六页不存在可识别的统一页面模板；
6. 重要动态均有氛围、控制或因果职责，不能只是装饰；
7. 不存在虚构客户、精确效果数字和伪造生产状态；
8. 影像属于同一个 Yonaris 世界，不像通用 AI 商务图库；
9. 移动端重新组织任务，不是桌面模块纵向堆叠；
10. Contact 清楚说明输入、人工处理与用户得到的下一步；
11. 不复制 Bluefish、Scrunch 或其他参考站的文字、图片、源代码和标志性组合；
12. 原型通过关键交互、横向溢出、控制台错误和 reduced-motion 检查。
13. 每个主交互必须改变共享内容或关系状态，并让输入、证据和输出保持确定性对应；只播放预设动画不算交互。鼠标拖动必须有键盘与触控等价路径。
14. 任何只在 hover 时出现的内容或控制，都必须能够通过键盘 focus 和触屏 tap 访问。

## 9. 工作与确认方式

用户只在两个节点参与：

1. 确认本设计规范；
2. 操作完整本地原型并判断效果。

原型制作期间不再要求用户选择页面方案、组件样式或动效细节。所有中间方案由设计者根据本规范自行审查。只有当新事实会实质改变品类、能力边界或客户承诺时，才暂停并请求用户决定。

在本文件获确认前，不进入实施计划或原型编码；在本地原型获确认前，不进入生产开发或发布。
